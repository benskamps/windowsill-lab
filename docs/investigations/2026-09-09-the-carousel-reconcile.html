01

What the receipts say

Not an inference. The archive, counted.

Milestone M01 reproduces Onsager's 1944 exact solution for the 2D Ising critical temperature. It has run forty-five times since June. Forty-one of those runs printed a byte-identical headline: χ peaked at T≈2.300 vs Onsager 2.2692. The four that differed read T≈1.600 and T≈1.500 — those are not discoveries, those are the estimator failing and being published as a result. M02 has run forty-four times.

Each bar is one committed M01 receipt, June → September. Height encodes the measured χ-peak. Forty-one agree to the last digit; the four in dusk-blue are the estimator's own failures, published as findings. A core sample from a tree that added no wood.

After the value-function planner landed on 14 August, the pattern changed shape but not substance: 110 receipts across 27 milestones, five to seven runs each — near-perfectly uniform. The planner did not fix the carousel. It balanced it.

03

Why the planner could not reach the frontier

Three mechanical causes. None of them is "nobody tried."

Cause 01 · the dispatch table

The frontier class had one seat, and it was gated shut

plan_turn admits an open milestone only if it has a registered runner. The eight that are the redefined product — C02, C03, C04, A06, I02, I03, B01, B02 — had none, so they were skipped silently on every turn. The one milestone actually marked open, A05, is lane-exhausted on this box. Every turn fell through to the canary board.

Cause 02 · the value function

Staleness paid the planner to replay

A verified canary's value scaled by log2(1 + days_since / half_life), capped at 4×. The longer a rung went unmeasured, the more the planner wanted it. It also broke the stated class order — a canary at 4.0 outranked a kept miss worth retrying at 3.0.

Cause 03 · the guard, and its test

The repeat law measured the wrong axis

repeats = head_run if mid == head_mid counts consecutive receipts. A 29-slot round-robin never repeats consecutively. Max consecutive run since the planner landed: 1. REPEAT_HARD_CAP = 3 has never fired. The guard was built for the June failure — M01 nightly, nineteen in a row — and the failure had already moved. The test suite pinned the same axis, so it stayed green throughout.

The deeper reason decay could never have worked: a carousel is a fixed point of any symmetric value function. Every rung pays the same decay each lap, nothing reorders, and the loop is stable. Breaking it needs an asymmetric term.

04

What was fixed

Planner v1 → v2. Old receipts are not regraded; they were honest under the law they were planned by.

curriculum.py

Staleness capped at due

STALENESS_CAP 4.0 → 1.0. A canary comes due at one half-life and never appreciates past it. Being ignored for another month does not make Onsager's constant more in need of remeasuring.

curriculum.py

Repeat saturation — the asymmetric term

Canary value divided by 1 + prior receipts. The 46th M01 run is worth 1/46th of the first. This is what a carousel cannot survive, because it prices samples already taken rather than time elapsed.

cli.py

The single-bench shortcut stops short-circuiting the planner

_select_next now declines when more than one milestone is open, so plan_turn arbitrates. Without this, opening C03 would have created a new carousel — one rung, every turn — and starved the A05 hunt outright.

curriculum.py

The reason line stopped lying about its own version

Four hardcoded "planner v1:" strings meant a receipt could carry planner: "v2" in its block while the prose beside it said v1.

tests/test_planner.py

The law the suite never had

test_an_all_canary_carousel_is_not_a_fixed_point — 120 turns over the real rotation; the board's own scores must exhaust as it laps, and one dispatchable frontier rung must take the turns back. The test that would have caught this in August.

05

What was built

lab c03 — the first of the eight to become dispatchable.

An OEIS b-file extension instrument, shaped as a gate rather than a run, because the standing failure mode is an instrument that cannot say unsure:

  • Reproduce — regenerate every term the b-file already holds and compare canonical bytes. One mismatch and the run refuses. We do not get to extend what we cannot reproduce.
  • Cross-verify — an algorithmically independent second method must agree. Two runs of one algorithm agree about their shared bug.
  • Price the reach — time the terms, project the cost, return in-reach/out-of-reach with the number. An out-of-reach verdict is a result.
  • Extend — inside the measured budget only, and a term is claimed only where both methods produce the same integer.

06

What the target search actually found

The honest half. This is the milestone, and it is still open.

The instrument is calibrated; the target is not chosen. Extending Motzkin numbers is not a contribution — that b-file stops at 2,106 by convention, not by difficulty. Three things were measured while looking for one that is both reachable and wanted:

Measurement

The famous short b-files are short because they are hard

A000105 (polyominoes) stops at n=59, A000170 (n-queens) and A007764 (self-avoiding rook paths) at 27. Every one is a standing record. There is no soft frontier hiding among the well-known sequences.

Measurement

OEIS publishes its own soft frontier, and it is empty

keyword:more means "more terms are needed"; keyword:easy means "easy to compute". Their intersection returns exactly one sequence — and it is a joke about the English names of numbers. Curation has already eaten the easy wins.

Instrument defect, caught by control

The search endpoint answers "too many" with the word null

HTTP 200, body null. A probe reading that as "zero results" reports an empty frontier that is in fact a crowded one — and my first pass did exactly that until a positive control caught it. It also rate-limits to 403 under steady polling. Both are now encoded in oeis_search.

Which sharpens what the r/vibecoding result actually was. Circle packing at N=101–114 was soft because it is a continuous optimisation nobody had thrown modern compute at, with a cheap exact verifier and a responsive human maintaining the record. That combination is the scarce thing — not the agent, and not the overnight cron.
